# 项目集成流程与任务标准

本方案的交付单位是一个可复制的项目目录，而非运行中的服务。把 `kit/.codex-tasks/` 和 `kit/.agents/` 复制到任意目标项目后，任务文件、项目配置、执行程序与 skill 都位于该项目内。Codex CLI 是唯一的任务执行进程；Python 脚本只负责读取计划、串行调度、验证和记录状态。

## 目录和职责

```text
目标项目/
├── .agents/skills/codex-task-planner/SKILL.md
└── .codex-tasks/
    ├── run.py                  # 统一命令入口
    ├── codex_task/             # 运行器代码
    ├── project.json            # 项目参数；按需修改
    ├── plans/                  # 实际任务定义，纳入版本控制
    ├── examples/               # 开发、非开发示例，不参与执行
    ├── WORKFLOW.md             # 项目内流程与格式标准
    ├── state.sqlite            # 本机进度，不提交
    └── runs/                   # 日志，不提交
```

skill 指导 Codex 根据项目需求拆任务、维护计划和恢复工作；它不能代替运行器持久记录进度。`.agents/skills/` 采用 [OpenAI 在仓库中使用 skill 的目录约定](https://developers.openai.com/blog/skills-agents-sdk)。项目已有 `AGENTS.md` 时继续遵循原有约定，不需要添加一套通用提示词覆盖项目规则。项目可以把 `.codex-tasks/WORKFLOW.md` 当作本地标准，并按需要调整任务质量要求。

## 五步工作流

1. **复制集成**：`python3 scripts/copy_to_project.py /path/to/project`，或手工复制上述两个隐藏目录。工具包的 `README.md` 不会覆盖目标项目文档。非 Git 项目把 `project.json` 的 `skip_git_repo_check` 设为 `true`。
2. **拆分目标**：读需求、`AGENTS.md` 和相关资料；每个任务限定为一次 Codex 调用可以独立完成的结果。把依赖放在同一计划中，用 `depends_on` 表达。计划文件写入 `plans/`，不在计划内存状态。
3. **校验计划**：运行 `python3 .codex-tasks/run.py validate`，修正 ID、路径、依赖、字段和检查命令。`status` 显示当前可运行与等待依赖的任务。
4. **执行与验证**：`run --max-tasks N` 按顺序执行 N 个任务；不设上限则直到全部完成或遇到需要处理的任务。运行器检查 Codex 结构化结果、预期产物和可选验证命令。`status --json` 适合持续集成或自己的脚本读取。
5. **恢复与交接**：任务 `blocked` 时本轮停止；下次 `run` 优先重试一次，仍阻塞则再次停止。`failed` 或 `interrupted` 后，`show PLAN_ID/TASK_ID` 查看运行目录与日志，修复后手动 `retry`。已完成任务定义变更后，`reconcile` 重置它及下游任务。交接报告状态、验证证据、剩余风险和下一条可执行命令。

## 格式标准

一个计划文件只描述一个目标。顶层为 `version: 1`、`plan`、`tasks`；`plan` 至少有唯一的 `id` 与标题。任务至少有唯一 `id`、`title`、`objective`、非空 `acceptance`。建议在需要时列出 `context`（已存在的输入路径）、`artifacts`（产出路径）、`depends_on` 和 `checks`。路径相对于目标项目根目录。ID 使用小写字母、数字、连字符，首字符为字母。依赖仅指向同一计划的任务 ID，不能形成环。

`checks` 用 `argv` 数组，例如 `[{"argv": ["python3", "-m", "pytest", "tests/test_example.py"]}]`。检查是目标项目提供的命令，不能假定所有项目都是 Python 项目。确需 shell 语法时，显式设置项目配置 `allow_shell_checks: true`。没有自动检查的内容可设 `require_review_without_checks: true` 进入人工验收，完成审阅后再 `accept`。JSON 计划使用标准库即可；YAML 计划可读性更好，但需安装 PyYAML。两者字段与语义一致。

通用任务拆分示例：开发任务先实现再写文档；非开发任务先整理项目内资料再校对结论。示例文件位于 `kit/.codex-tasks/examples/`，复制到 `plans/` 后要把占位目标和检查命令改成项目真实内容。不要将示例直接作为真实任务执行。

## 状态与完成标准

运行器使用 SQLite 保存本机任务状态和每次尝试，原因是它只需 Python 标准库、无需数据库服务，并能在进程中断后继续查询；这是实现细节，项目成员只通过 CLI 操作。一个任务只有在 Codex 返回完成、预期文件存在、所有检查成功，并满足项目设定的人工审阅条件后才算完成。`failed`、`blocked`、`interrupted`、`needs_review`、`changed` 都不等于完成。整个目标完成还需核对用户需求与项目级验收，不只看任务计数。

运行器只管理本地项目工作，不应在计划中默认执行提交、推送、部署或写外部系统；这些动作受用户授权和项目规则约束。串行执行避免同一工作区多个 Codex 进程互相覆盖。升级工具时保留 `project.json`、`plans/`、`state.sqlite`、`runs/`，并在项目副本中先验证兼容性。
